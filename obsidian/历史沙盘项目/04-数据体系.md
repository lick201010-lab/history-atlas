## 文明数据

`dynasties.json` 目前已经不是最小 MVP 结构，而是可以支撑信息面板、筛选、对比和事件叙事的完整条目。

核心字段包括：

- `id`
- `name`
- `nameEn`
- `startYear`
- `endYear`
- `capital`
- `color`
- `region`
- `summary`
- `events`
- `relatedLandmarks`
- `tags`
- `importance`
- `legacy`

## 边界数据

`boundaries-simplified.json` 是一个 `FeatureCollection`，当前总数 89，说明已经不是“43 个文明 = 43 条边界”的最初状态，而是部分文明按 phase 拆分了多个 feature。

常见字段：

- `id`
- `dynasty` / `dynastyId`
- `phase`
- `phaseLabel`
- `startYear`
- `endYear`
- `color`
- `capital`
- `summary`
- `accuracy`
- `accuracyLabel`
- `accuracyNote`
- `sourceNote`
- `geometry`

### 当前精度层次

- `rough`
- `rough-refined`
- `coastline-aware-rough`

这些字段不仅影响说明文本，也直接影响 `MapScene.jsx` 中的渲染分支。

## 时代数据

`eras.json` 当前有 8 个时代，用于时间轴叙事和事件浮层。它仍是产品叙事层，而不是严格学术分期系统。

## 校验机制

`scripts/validateHistoricalData.mjs` 会校验：

- 文明字段完整性
- 年份合法性
- landmark 引用存在性
- 边界 ring 闭合与坐标合法
- 样板边界必要说明字段
- `modelProfile` 覆盖关系
- GLB 资产审计另由 `scripts/auditGlbAssets.mjs` 负责，检查 `public/models/*.glb`、`createBuildingLayer.js` 覆写映射、z-up orientation、体积、贴图、三角面、贴地 `minZ`。

当前真实数据是 43 个文明、89 个边界 feature、30 个地标、14 个 GLB 重点奇观；文档引用时应优先以 `npm run validate:data` 与 `npm run audit:glb` 的输出为准。

## 当前数据工作原则

- 不把三大 JSON 当手工笔记直接乱改。
- 批量变化优先脚本生成。
- 任何数据扩展都要跟 `validateHistoricalData.mjs` 一起维护。
- 精修边界必须保留 `accuracyNote` / `sourceNote`。
- 后续学术化必须补上 citation / references 体系。

## 当前数据系统的核心矛盾

- 产品已经需要更精细的边界和建筑说明。
- 但数据仍然主要服务视觉产品，而不是学术数据库。
- 所以下一步最值钱的不是“再塞更多条目”，而是提高重点样板的可信度和说明质量。
