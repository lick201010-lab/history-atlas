# 下一步路线图

## 优先级判断

基于当前本地项目状态，下一步不应该再写一个“什么都想做”的大清单，而是按真实阻塞顺序推进。

## P0：验证当前未提交地图精修是否成立

目标：

- 确认 dark 主题装裱框、边界平滑、casing、viewport padding 在真实浏览器里确实提升体验

任务：

- 用真实浏览器检查右侧最边缘区域是否仍被面板挡住
- 检查高俯仰是否出现黑屏或错位
- 检查 map resize 延时策略是否稳定
- 检查边界平滑后是否出现意外几何变形

说明：

这一步最适合 Codex 做，因为它是验收性质，不是大批量实现。

## P1：把边界方法从样板扩到更多重点文明

目标：

- 让 coastline-aware 不再只停留在少数代表项

任务：

- 选下一批高优先文明
- 按 `docs/BOUNDARY_REFINEMENT_METHODOLOGY.md` 做 phase 化和多包络裁切
- 同步更新校验口径和说明字段

说明：

这一步适合 Claude 主做，Codex 抽查和验收。

## P1：建立 GLB 样板的统一验收基线

目标：

- 不再靠主观描述判断“这个奇观好不好”

任务：

- 对 5 个已提交 GLB 统一做截图对照
- 记录地图视角下的识别度、体积、缺陷
- 决定哪些值得继续做，哪些暂时保留程序化版本

说明：

现在最缺的不是“再多做 5 个 GLB”，而是建立样板质量判定标准。

## P2：统一文档计数和验收口径

目标：

- 消除“README 说 43 边界，实际是 89 feature”这类信息漂移

任务：

- 更新 README 的边界数量表述
- 更新 `docs/ACCEPTANCE.md`
- 统一 Obsidian、README、验收文档中的数据规模描述

说明：

这是文档债，不解决会长期干扰协作。

## P2：补引用与可信度体系

目标：

- 让重点文明、重点边界、重点建筑开始具备可追溯说明

任务：

- 先从样板文明和样板奇观开始
- 给 event / boundary / landmark 补更规范的来源字段
- 形成轻量引用规范

说明：

当前项目最大短板已经从“没功能”转为“可信度不足”。

## P3：性能与资源加载优化

目标：

- 在不牺牲当前体验的前提下给后续扩展留余地

任务：

- 评估 MapLibre / Three / JSON / GLB 的增长趋势
- 判断是否需要更明确的懒加载
- 评估移动端 GPU 和内存压力

说明：

这一步重要，但不应早于当前视觉与内容基线稳定。

## 当前不建议优先做的事

- 不建议重新摇摆到 globe 或其他地图引擎
- 不建议在 atlas 主题上继续做激进探索
- 不建议为了“更精细”盲目批量堆更多 GLB

## 推荐执行顺序

1. 验证本地未提交 dark 地图改动
2. 统一 5 个 GLB 样板验收标准
3. 扩下一批重点文明边界
4. 修正文档计数和验收口径
5. 补引用体系
