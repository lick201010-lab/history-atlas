# 当前问题与风险

## 1. 本地状态与线上状态不一致

当前仓库是 dirty worktree，本地有未提交的 dark 主题地图视觉与边界渲染修改。

风险：

- 文档写成“当前如此”，但 GitHub 和生产并不是这个状态
- 后续回看时难判断哪部分已经被验证过

应对：

- 所有说明都明确区分“已提交”与“未提交”
- 部署前必须先做真实浏览器验收，再决定是否提交和上线

## 2. 边界观感改善不等于边界真实性改善

运行时 Chaikin 平滑和 casing 可以让边界更好看，但不会把错误的边界变成正确边界。

风险：

- 团队误把“圆滑了”当成“精确了”
- 用户继续对海岸贴合度不满

应对：

- 继续扩展 coastline-aware 方法
- 对重点文明坚持 phase 化和 sourceNote / accuracyNote

## 3. 圣索菲亚与样板奇观仍未形成最终质量闭环

虽然已经有 5 个 GLB 样板，但 `WORK_LOG.md` 明确显示用户对圣索菲亚效果仍未完全认可。

风险：

- 团队过早宣布“3D 资产问题已解决”
- 继续在程序化细节上投入过多时间，收益下降

应对：

- 用地图视角截图做统一验收
- 区分“重点奇观 GLB 化”与“普通地标继续程序化兜底”

## 4. 当前文档口径存在早期残留

README 和部分旧文档仍保留“43 个边界”的早期描述，但本地实际数据已经是 89 个 feature。

风险：

- 口径不一致，后续协作时产生误判
- 验收基线和真实数据不一致

应对：

- 以后引用计数优先以当前本地数据为准
- README / 验收清单后续应补一次统一更新

## 5. 视觉方向仍可能被“风格冲动”带偏

dark 主题当前在做装裱框、星空边距和更强边界光效试验。这个方向有潜力，但也容易过度设计。

风险：

- 画面变得“看起来很努力”，但信息密度下降
- 地图主体被装饰吞掉

应对：

- 视觉验收必须回到：边界是否更清楚、地图是否更好操作、信息面板是否更不挡视野

## 6. 外部依赖仍是线上不稳定点

- CARTO 底图
- AWS DEM

风险：

- 网络差时首屏和地图体验不稳定
- 国内访问会受外部网络影响

应对：

- 现阶段接受这一现实
- 等产品形态更稳后再评估自建瓦片

## 7. 构建体积与资源体积仍需盯住

MapLibre、Three、本地 JSON 和 GLB 都在增长。

风险：

- 首屏更慢
- 移动端 GPU / 内存压力上升
- 后续每加一个重点 GLB 都会累积成本

应对：

- 继续控制单个重点 GLB 体积
- 未来考虑更明确的懒加载策略

## 8. 协作文档与真实实现可能漂移

项目现在同时有：

- README
- docs/*
- WORK_LOG
- Obsidian 笔记

风险：

- 一处更新，三处没改
- 新成员不知道该信哪一份

应对：

- 部署事实信 `docs/ALIYUN_GITHUB_DEPLOYMENT.md`
- 会话过程信 `WORK_LOG.md`
- 项目结构和阶段判断信 Obsidian

## 当前最现实的总风险判断

这个项目现在最大的风险不是“技术栈选错了”，而是：

- 容易把局部视觉改善误判为整体体验成熟
- 容易把本地实验状态误写成项目正式状态
