# 当前问题与风险

## 1. 局部视觉改善不等于整体体验成熟

dark 主题、移动端 HUD、边界 glow/casing、奇观 GLB 都已经推进，但它们仍需要统一地图视角验收。

风险：

- 单点看起来更精致，但组合后遮挡、抢视觉、信息密度下降。
- 手机端与桌面端验收标准混在一起。

应对：

- 每次视觉变更必须跑 `npm run check`。
- 关键变更后用桌面和 390px 手机视口各做一次浏览器验收。
- 视觉验收回到：边界是否更清楚、地图是否更好操作、信息面板是否更不挡视野。

## 2. 边界观感改善不等于历史真实性改善

运行时 Chaikin 平滑和 casing 可以让边界更好看，但不会把错误边界变成可信边界。

风险：

- 团队误把“圆滑了”当成“精确了”。
- 海岸线或岛屿仍可能因为粗包络而错位。

应对：

- 继续扩展 coastline-aware 方法。
- 重点文明坚持 phase 化和 `sourceNote` / `accuracyNote`。
- 后续边界任务更适合 Claude 批量实现，Codex 负责校验和抽查。

## 3. GLB 数量增加后，质量漂移会更快

当前已接入 14 个重点奇观 GLB，不再是 5 个样板。数量变多后，最危险的不是“没有模型”，而是：

- 某些模型过低模，地图视角像粗图标。
- 某些模型 orientation 漏接导致倒放。
- 文件存在但映射漏了，或映射存在但部署缺文件。
- 体积逐步增加，移动端压力上升。

应对：

- `npm run audit:glb` 已加入 `npm run check`。
- `docs/GLB_ASSET_BASELINE.md` 作为资产事实基线。
- WARN 资产先做地图视角截图 QA，再决定是否精修。
- 不建议盲目“一次性做 30 个”，应该按质量样板逐步扩展。

## 4. 文档口径仍可能漂移

项目同时有 README、docs、WORK_LOG、Obsidian、AGENT.md。任何一处没同步，后面都会影响 Claude / Codex 分工。

风险：

- 旧文档保留“43 个边界”“5 个 GLB”等早期口径。
- 新 agent 根据旧数字做计划，导致任务重复或方向错误。

应对：

- 数据规模优先以 `npm run validate:data` 与 `npm run audit:glb` 输出为准。
- 部署事实信 `docs/ALIYUN_GITHUB_DEPLOYMENT.md`。
- 会话进度信 `WORK_LOG.md` 与 `AGENT.md`。
- 项目结构和阶段判断信 Obsidian。

## 5. 外部依赖仍是线上不稳定点

- CARTO 底图。
- AWS DEM。
- MapLibre / Three 资源体积。

风险：

- 网络差时首屏和地形体验不稳定。
- 国内访问会受外部瓦片服务影响。
- 移动端 GPU / 内存压力上升。

应对：

- 现阶段接受外部瓦片依赖。
- 产品形态更稳定后再评估自建瓦片或更轻的地形策略。
- 后续考虑更明确的懒加载和资源分组。

## 当前最现实的风险判断

项目当前最大风险不是技术栈选错，而是：

- 把局部改善误认为整体成熟。
- 把“GLB 数量增加”误认为“奇观质量达标”。
- 把文档旧口径当成当前事实。
