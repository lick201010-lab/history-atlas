# 部署与运维

## 线上事实

- 生产地址：`https://atlas.ckl.hk`
- 服务器：阿里云 ECS
- IP：`47.237.181.181`
- 系统：Ubuntu 24.04.x LTS
- Web 服务：Caddy v2
- 静态目录：`/opt/history-atlas/dist`
- 同机项目：`lottery-analysis`

## 当前正式部署模式

当前不是“服务器拉源码构建”，而是：

1. 本地 Windows 跑 `npm run check`
2. 本地生成 `dist/`
3. `scp` 上传到 `/opt/history-atlas/dist`
4. 远端修权限
5. 校验首页、SPA fallback、分块资源

也就是 README 和部署文档里写的“本地构建 + 静态上传”模式。

## 为什么坚持本地构建

`AGENT.md` 和 `docs/ALIYUN_GITHUB_DEPLOYMENT.md` 都给出过同一个结论：

- 服务器内存有限
- 同机还有 lottery 服务
- 不值得在服务器上冒 OOM 风险去跑 Vite / Rollup 构建

所以对这个项目而言，部署脚本的价值不是“炫技自动化”，而是把低内存服务器风险降到最低。

## 当前 deploy 脚本口径

`npm run deploy` 对应：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/deploy.ps1
```

它的职责是：

- 检查本地工具
- 执行 `npm run check`
- 确认 `dist` 产物
- 上传 `dist/*`
- 修复远端静态文件权限
- 校验线上首页、随机路径、JS/CSS chunk

它明确不做：

- 不改 `/opt/lottery-analysis`
- 不修改 Caddyfile
- 不 reload Caddy
- 不在服务器上跑构建

## Caddy 配置事实

线上站点依赖这个思路：

```caddy
atlas.ckl.hk {
    root * /opt/history-atlas/dist
    file_server
    try_files {path} /index.html
    encode gzip zstd
}
```

即静态目录 + SPA fallback + 自动 HTTPS。

## 当前运维文档中的一个重要现实

项目的 README、部署文档、AGENT 都已经把“只改静态文件即可上线”写清楚了，所以对 Codex 来说，日常最关键的不是重新设计运维，而是：

- 别误动 Caddy
- 别误伤 lottery
- 别把“本地能 build”误写成“已经部署”

## 本轮自动化更新中的部署结论

- 本次只更新 Obsidian 笔记
- 没有执行 `npm run deploy`
- 没有执行服务器变更
- 没有修改生产文件

这条结论应该保留，避免后续误读为“文档一更新就已经发版”。

## 当前运维风险

- `scp` 方式不会自动删除旧 hashed asset
- 外部瓦片和 DEM 依然是线上体验不稳定源
- 本地存在未提交 UI 工作，意味着线上与本地视觉状态不一致

## 后续运维关注点

- 若未来静态文件体积继续增长，考虑更明确的同步清理策略
- 若国内访问稳定性成为重点，再评估自建瓦片
- 任何 dark 主题大改上线前，都必须先做真实浏览器验收，而不是只看构建通过
