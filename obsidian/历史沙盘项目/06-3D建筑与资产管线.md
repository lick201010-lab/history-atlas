# 3D 建筑与资产管线

## 当前实现结构

建筑层由 `src/map/createBuildingLayer.js` 统一管理，当前是两层体系：

1. 程序化 builder 负责基础可见性、fallback 和普通地标。
2. 重点奇观通过 `public/models/*.glb` 覆写，提高地图视角下的轮廓辨识度。

GLB 是异步加载的：页面先显示程序化模型，GLB 加载成功后替换主体 mesh；失败时保留 fallback，不影响地图可用性。

## 当前真实规模

以 2026-06-02 本地审计为准：

- `landmarks.json`：30 个地标。
- `createBuildingLayer.js`：14 个 GLB override。
- `public/models/`：14 个 GLB 文件。
- 总 GLB 体积：约 4.18 MB。
- `npm run audit:glb`：13 OK / 1 WARN / 0 FAIL。

唯一 WARN 是 `chichen-itza`：三角面过低，需要后续视觉 QA 确认轮廓是否太粗。

## 自动审计

新增脚本：

```bash
npm run audit:glb
npm run audit:glb -- --write
```

它会检查：

- GLB 文件是否存在。
- `ID_GLB_OVERRIDES` 是否和文件对齐。
- `ID_GLB_ORIENTATION_OVERRIDES` 是否覆盖所有 GLB。
- 是否含贴图或图片。
- 文件体积是否超过预算。
- 三角面是否超过硬上限或过低。
- `minZ` 是否低于地面。

审计报告写入：

- `docs/GLB_ASSET_BASELINE.md`

以后判断“当前到底有几个 GLB、哪些有风险”，优先看这份自动报告，而不是旧聊天记录。

## 当前资产判断

不能再说“项目只有 5 个 GLB 样板”。更准确的说法是：

> 项目已有 14 个重点奇观 GLB 覆写，但仍处在“低模精品化样板期”，不是最终真实建筑复原。

这点很重要，因为用户追求的是“地图视角下一眼能认出、质感精美”，不是只要技术上加载了 GLB。

## 下一步最合理的资产路线

短期：

- 用 `docs/GLB_ASSET_BASELINE.md` 固定资产事实。
- 对 14 个 GLB 做地图视角截图 QA。
- 优先处理 WARN 和用户肉眼反馈不佳的资产，而不是盲目新增更多 GLB。

中期：

- 将低辨识度资产提升到圣索菲亚 / 斗兽场 / 泰姬陵这类更高细节档。
- 继续用 `scripts/lib/wonderKit.mjs` 保持统一建模原语和导出流程。
- 每新增或重建一个 GLB，都必须跑 `npm run audit:glb`。

长期：

- 建立 LOD 或懒加载策略。
- 为重点奇观补来源、造型说明和截图验收记录。
- 普通地标继续程序化兜底，重点奇观才进入 GLB 精修。
